### 自動更新（§10.2、§10.3）

| 段階 | 内容 |
|---|---|
| 確認 | 起動の約5秒後に非同期で `releases/latest` を確認（初期値 ON）。成功した確認から24時間は確認しない（複数ウィンドウで共有）。「ヘルプ → 更新を確認」はすぐ確認。下書き・プレリリースは対象外。バージョンは数値で比較 |
| 検査 | タグ `vX.Y.Z`、アセット名 `MediaViewer-X.Y.Z-x64.msi`（重複・アップロード途中・過大なサイズは拒否）、ダウンロードURLが正規リポジトリのパスと完全一致、転送先は HTTPS の github.com／*.githubusercontent.com のみ（1段ずつ検査） |
| ダウンロード | 既定で自動（設定で OFF 可）。バックグラウンドで行い、画面には準備ができてから通知。複数ウィンドウでは1つだけがダウンロード。途中で止まったら（60秒無通信）中止し、書きかけのファイルは消す |
| 検証 | サイズ、GitHub の digest（SHA-256）、ECDSA P-256 の署名（アプリに埋め込んだ公開鍵）。署名の対象は「ファイル名・版・サイズ・SHA-256」なので、古い版の正規ファイルを新しい版と偽ることもできない |
| 適用 | 既定は終了時に自動（最後のウィンドウを閉じたとき）。設定で「終了時に確認」も選べ、延期できる。「今すぐ再起動して更新」は確認のうえ実行（変換中・他のウィンドウがあるときは断る）。シャットダウン中は始めない |
| 更新プログラム | `%LocalAppData%` へ複写して起動。アプリの終了を待ち、MSI を書き込み禁止で開いたまま再検証し、msiexec だけを UAC で昇格して実行 |
| 起動確認 | 新しい版の `MediaViewer.exe --health-check`（画面定義・描画・再生ライブラリ・FFmpeg の読み込み、ウィンドウは出さない、約0.9秒）と、ファイルのバージョン番号を確認 |
| ロールバック | 起動確認に失敗したら直前の版の MSI を入れ直す。直前の版の MSI は保存しておく（なければ現在の版のリリースから取得して検証） |
| 結果の表示 | 次に起動したとき、更新の結果（成功・見送り・失敗・ロールバック）を一度だけ表示 |
| 障害時 | 通信エラー・レート制限・オフラインでも他の機能はそのまま使える。自動確認の失敗は表示せずログのみ。設定は `%LocalAppData%` にあり、更新・ロールバックで消えない |

### リリースの自動化（§10.4）

| ワークフロー | 内容 |
|---|---|
| CI（main への push・PR） | ビルドと単体テスト |
| FFmpeg ビルド | MSYS2 で必要な機能だけの FFmpeg をビルドし、ソースとライセンス文を付けてプレリリース（`ffmpeg-9.0.2-mvN`）に添付 |
| リリース（`v*` タグ） | テスト（同梱 FFmpeg での変換の結合テストを含む）→ 発行 → 起動確認 → MSI 作成 → 署名（秘密鍵は Secrets から環境変数で渡し、埋め込みの公開鍵で確認）→ 下書きで全アセットを添付してから安定版として公開。タグの説明文がリリースノート。手動実行では公開せず成果物の保存のみ |

## 2. テスト

単体テスト 171 件（Phase 4 から 70 件追加）がすべて成功。CI（GitHub Actions）でも成功。

- バージョン番号：数値比較（1.10.0 > 1.9.0）、プレリリースの順序、`v` 付きタグ、ビルド情報（`+…`）の無視、不正な形式の拒否、24時間の間隔（時計が戻った場合も確認する）
- リリースの検査：下書き・プレリリース・不正なタグ・他のリポジトリやタグを指す URL・HTTP・クエリ付き URL・`file:` の拒否、アーキテクチャ違いや重複アセット、アップロード途中、過大な署名ファイル、digest の形式
- 署名：署名と検証、サイズ・版・ファイル名・ハッシュのどれが変わっても検出、別の鍵の署名、壊れた署名、埋め込みの公開鍵が P-256 であること
- ダウンロード（偽の GitHub を使用）：新しい版の検出、同じ版・古い版・リリースなし、レート制限とオフラインのメッセージ、検証済みなら再ダウンロードしない、別の版として署名されたファイル・別の鍵・digest の不一致・途中で切れた／大きすぎるデータ・想定外のホストや HTTP への転送を拒否し、書きかけのファイルを残さないこと、ロールバック用の現在の版の取得
- 更新ファイルの保存場所：残す版の判定（現在・新しい版・直前の版）、更新結果の一度だけの表示、ダウンロードの排他
- 更新プログラムの引数：空白を含むパスの受け渡し、不正な引数の拒否
- インストーラー：ファイルの関連付けの拡張子と種別がアプリの対応形式と一致すること

アプリ・更新プログラムでの確認：

- 開発ビルドを起動し、起動5秒後の自動確認で GitHub API に接続（リリース未公開のため「最新」）、確認日時が設定に保存されることを確認
- `--health-check`：正常な発行版で終了コード 0（約0.9秒）。再生ライブラリを削除した版では「再生」「変換」の失敗を記録して終了コード 1
- 更新プログラム（Native AOT）：署名の検証に失敗する MSI では msiexec を起動せず「失敗」の結果を記録。不正な引数では何もせず終了
- 署名ツール：実際の秘密鍵で署名し、アプリに埋め込んだ公開鍵で検証できることを確認（鍵の取り違えがないこと）
- MSI：作成し、全ユーザー向け（ALLUSERS=1）であること、旧版の削除が InstallInitialize の直後（同じトランザクション）にあること、更新プログラムと FFmpeg が含まれることを確認

GitHub Actions でのリリースの試行（手動実行、バージョン 0.0.1、公開はしない）：すべての段階が成功。

## 3. 自前ビルドの FFmpeg（D12）

| 項目 | 内容 |
|---|---|
| 版 | FFmpeg 9.0.2（公式ソースを SHA-256 で確認）、MSYS2 UCRT64・GCC 16.2 でビルド、`9.0.2-mediaviewer1` |
| 構成 | 共有ライブラリ、GPL。ネットワーク・デバイス・合成ソースは無効。プロトコルは file と pipe のみ |
| エンコーダー | H.264（x264）、VP9（libvpx）、AAC、Opus、MP3（LAME）、Vorbis、FLAC、PCM 16/24bit、mov_text、WebVTT、WebP（libwebp）、MJPEG、PNG |
| 書き出し形式 | MP4、MOV、M4A（ipod）、MKV、WebM、AVI、MP3、WAV、FLAC、OGG、WebP |
| 読み込み | デコーダー・読み込み形式はすべて有効（AV1 は dav1d） |
| サイズ | 35 MB（展開後）、zip で 14.5 MB。開発で使った公式配布の GPL 版（ffmpeg・ffprobe・ffplay 各約 157 MB）から大幅に縮小 |
| ライセンス | zip の licenses フォルダに FFmpeg と各ライブラリのライセンス文、ビルド構成、同梱パッケージの版を収録。FFmpeg と GPL／LGPL ライブラリのソースは同じプレリリースに添付 |
| 確認 | 必要なエンコーダーが含まれることをビルド時に確認。変換の結合テスト（40件）がこのビルドで成功 |

ビルドで直した点：MSYS2 の iconv.h に対して configure がリンク指定を加えない問題（`-liconv` を明示）、mov_text エンコーダーの configure 上の名前（`movtext`）。結合テストは、最小構成の FFmpeg にない合成ソース（lavfi）や PNG・SRT の書き出しに頼らないよう、入力をテスト内で作るように変更した。

## 4. 実機でのインストール・更新・ロールバック試験（2026-10-21、開発者が UAC を操作）

試験用に 0.0.1・0.0.2（正常）と 0.0.3（起動確認に失敗するよう再生ライブラリを抜いた版）の MSI を作り、実際の署名鍵で署名した（各約 59 MB）。更新は実際の更新プログラムに、アプリと同じ引数を渡して実行した。試験中に起動したアプリは試験用の設定ファイルを使った。

| # | 確認 | 結果 |
|---|---|---|
| 1 | 0.0.1 をインストーラーの画面でインストール | 成功。363 ファイル、「アプリと機能」（発行元・URL、変更・修復なし）、スタートメニュー、「プログラムから開く」、既定のアプリの候補の登録を確認。完了画面からアプリが起動 |
| 2 | 更新プログラムで 0.0.1 → 0.0.2 | 成功（11〜14 秒）。起動確認に成功、旧版の登録は消え 1 件のみ。設定は変わらない |
| 3 | 更新プログラムで 0.0.2 → 0.0.3（壊れた版） | 1 回目は**失敗**（下記）。修正後は、0.0.3 の起動確認の失敗を検出して 0.0.2 を入れ直し、0.0.2 の起動確認に成功（24 秒、結果「ロールバック」）。次の起動で「直前のバージョンに戻しました」を一度だけ表示 |
| 4 | アンインストール | 成功。インストール先・ショートカット・関連付け・登録がすべて消え、設定ファイルとログは残る |

見つけた不具合：ロールバック（古い版の入れ直し）で、MediaViewer.exe など版番号を持つアプリ自身のファイル 5 個が欠け、アプリが起動できなくなった。既定のファイル置き換え規則では「入っている方が新しい」ファイルを複写しないと判断し、直後の旧版の削除がそれらを消すため。MSI に REINSTALLMODE=dmus（版が異なれば新旧に関係なく置き換える）を設定して解決し、壊れた状態からの入れ直し（ダウングレード）とロールバックの両方で全ファイルがそろうことを確認した。このとき更新プログラムは「直前の版にも戻せませんでした」の通知を正しく表示した。

GitHub Releases を経由した確認（アプリが新しい版を見つけてダウンロードし、終了時に更新する流れ）は、最初の安定版を公開した後、その次の版を公開したときに確認できる。

## 5. 既知の制約・今後の確認

| 項目 | 内容 |
|---|---|
| SmartScreen の警告 | コード署名証明書を使っていないため、ダウンロード時・初回の実行時に警告が出ることがある（README とリリースノートに対処方法を記載）。更新ファイルの真正性は自前の署名で確認している |
| 更新時の UAC | Program Files へのインストールのため、更新を適用するたびに管理者権限の確認が出る（D10、利用者の指定） |
| ロールバックの範囲 | 直前の版にだけ戻せる。直前の版の MSI を保存できなかった場合（リリースが削除されたなど）は戻せないため、その旨を表示する |
| WebP の表示 | 画像の表示は Windows の WebP コーデック（Windows 11 は標準搭載）を使う。コーデックを削除した環境では WebP を開けない |
| トリミングの警告 | 発行時に Windows SDK・C#/WinRT・SharpGen のトリミング警告（IL2104）が出る。起動確認は成功しているが、全機能の確認は Phase 6 で発行版を使って行う |
| GitHub 経由の更新 | アプリが GitHub Releases から新しい版を見つけてダウンロードし、終了時に適用する一連の流れは、2つ目の安定版を公開したときに実地で確認する |
